Пакетный менеджер - инструмент, ищущий, устанавливающий, обновляющий и удаляющий программы и их зависимости. 
ncdu - утилита позволяющая перемещаться по директориям и находить, что именно занимает место. В debian ее нет, на ее примере рассмотрим весь жизненный цикл пакета.
**Пакет** - это установочная единица в системе.
В Debian обычно используются .deb пакеты. 
Пакет может содержать:
- исполняемые файлы
- библиотеки
- документацию
- конфигурационные файлы
- информацию о зависимостях
- служебные скрипты, которые выполняются при установке, обновлении или удалении
Проще говоря, пакет - это архив с программой, в который также зашиты описание того, как эту программу правильно установить, какие компоненты ей нужны и как потом корректно удалить её из системы.![[Pasted image 20260908132902.png]]

### **apt и dpkg**
![[Pasted image 20260908133508.png]]
Состояния пакетов в **apt-mark**:
- **auto** - пакет установлен автоматически как зависимость. Если основная программа будет удалена, **apt** предложит удалить и его
- **manual** - пакет установлен пользователем вручную. Система не удалит его при автоматической очистке
- **hold** - пакет зафиксирован в текущей версии и не будет обновляться, пока статус не будет снят
Утилита **apt** удобна для повседневной работы, потому что она работает с репозиториями и зависимостями. Команда `sudo apt install ncdu` не просто устанавливает пакет, а автоматически проверяет необходимые зависимости, определяет, откуда их скачать, и вносит все нужные изменения в систему. 
Утилита`dpkg` работает на более низком уровне. Он полезен, когда нужно посмотреть состояние уже установленного пакета, список его файлов или установить локальный **.deb**-пакет. Стоит учесть, что **apt** тоже умеет устанавливать локальные **.deb-файлы** следующей командой - `apt install ./package.deb`. В отличие от **dpkg**, в этом случае автоматически 
подтягиваются недостающие зависимости из репозиториев.
### **Где apt хранит настройки и данные**
Утилита **apt** хранит настройки и служебные данные в нескольких местах файловой системы. Посмотрим директорию **/etc/apt.**
![[Pasted image 20260908144457.png]]
Файлы в **/etc/apt/sources.list.d/** позволяют разделять разные источники пакетов по отдельным конфигурационным файлам.
**apt** не обращается к репозиториям каждый раз с нуля. Сначала он скачивает списки **доступных пакетов** и хранит их **локально**.
Дистрибутивы Linux используют разные модели обновления. В дистрибутивах со **стабильными релизами** (Debian, Ubuntu LTS) версии пакетов фиксируются на момент выпуска и получают только исправления безопасности, такой подход обеспечивает предсказуемость, но пакеты со временем устаревают. В дистрибутивах с моделью **rolling-release** (Arch Linux, Manjaro) пакеты обновляются непрерывно до самых свежих версий, что даёт доступ к новым функциям, но увеличивает риск сбоев при обновлении.

### **Обновление списка пакетов**
Перед установкой новой программы обновим локальный список доступных пакетов - `sudo apt update`
**sudo** используем, потому что **apt update** изменяет системные файлы в **/var/lib/apt/lists/**, обычный пользователь не имеет на это прав.
Команда **apt search** ищет пакет по названию и описанию. Вот мы нашли в репозиториях **ncdu**, теперь посмотрим подробную информацию - `apt show ncdu`
В выводе можно увидеть:
- **Package** - имя пакета
- **Version** - доступная версия
- **Priority** - приоритет пакета
- **Section** - категория утилиты
- **Maintainer** - ответственный за обновления репозитория
- **Installed-Size** - размер после установки
- **Depends** - зависимости пакета
- **Description** - описание
### **Файлы пакета**
Пакетный менеджер отслеживает принадлежность каждого файла, позволяя точно знать, что установил пакет, и корректно удалить его без ручного поиска файлов по системе. Для просмотра списка файлов, установленных конкретным пакетом, используется команда `dpkg -L`. Пакетный менеджер отслеживает, какие файлы принадлежат каждому пакету.
### **Проверка состояния установленного пакета**
После установки пакета нужно убедиться, что он действительно установлен и работает корректно. Пакетный менеджер хранит информацию о состоянии каждого пакета - установлен ли он, какая версия стоит, какие у него зависимости. Посмотрим состояние пакета командой `dpkg -s ncdu`
![[Pasted image 20260908152045.png]]
В выводе можно увидеть поля:
- **Package** - имя пакета
- **Status** - состояние пакета (если пакет установлен корректно, то там будет написано **install ok installed**)
- **Version** - установленная версия
- **Architecture** - архитектура
- **Depends** - зависимости
- **Description** - описание
Также можно найти пакет среди установленных с помощью команды `apt list --installed | grep ncdu`
### **Зависимости пакета**
Программы в Linux используют общие библиотеки и компоненты, которые поставляются отдельными пакетами. Такие пакеты называются зависимостями. При установке программы пакетный менеджер автоматически настраивает всё необходимое, а при удалении может предложить убрать зависимости, которые больше не нужны.

Команда `apt depends ncdu` покажет, какие пакеты нужны для работы **ncdu**. Обратные зависимости можно посмотреть с помощью `apt rdepends ncdu`
### **Проверка состояния установленного пакета**
Со временем в репозиториях появляются новые версии пакетов с исправлениями ошибок, закрытием уязвимостей и новыми функциями. Чтобы система оставалась актуальной и безопасной, установленные пакеты необходимо периодически обновлять. Для этого обычно используют следующую последовательность: `sudo apt update && apt list --upgradable && sudo apt upgrade`

Разберём её по шагам. Сначала обновляем локальный список доступных пакетов (sudo apt update), затем смотрим, какие установленные пакеты можно обновить (apt list --upgradable)
И только после этого запускаем обновление (sudo apt upgrade). 
Команда **apt upgrade** может обновить много пакетов сразу. Поэтому перед подтверждением нужно прочитать список изменений.
> Особенно внимательно нужно относиться к обновлениям на рабочих системах, где запущены сервисы. **Обновление библиотек**, **демонов** или **системных компонентов** может потребовать **перезапуска служб**.

### **Удержание пакета от обновления**
Иногда конкретный пакет нужно временно запретить обновлять. Например, если новая версия ведёт себя нестабильно или обновление нужно отложить до запланированного обслуживания. Для этого используется команда `sudo apt-mark hold`. Это также позволяет обновлять остальную систему, не затрагивая зафиксированный пакет. Некоторое программное обеспечение (к примеру, **Kubernetes**), рекомендует фиксировать свою версию сразу после установки и обновлять его отдельно от системы, чтобы избежать несовместимости.

Чтобы проверить, какие пакеты сейчас стоят на удержании - `apt-mark showhold`. Если пакет больше не нужно удерживать, ограничение снимается командой `sudo apt-mark unhold`
### **Удаление пакета**
Теперь удалим **ncdu** с помощью команды `sudo apt remove ncdu`. Команда удаляет пакет, но может оставить конфигурационные файлы.
Снова установим пакет (`sudo apt install ncdu`) и рассмотрим второй способ удаления через **purge** - `sudo apt purge ncdu`
Команда **apt remove** удаляет пакет, но может оставить его конфигурационные файлы в системе. Если нужно удалить пакет полностью, вместе с конфигурациями, используется **apt purge**.
### **Очистка ненужных зависимостей**
После удаления пакета в системе могут остаться зависимости, которые были установлены автоматически и больше никому не нужны. Для их удаления используется команда `sudo apt autoremove`
### **Очистка кэша пакетов**
**apt** может хранить скачанные **.deb**-пакеты в кэше. Посмотреть кэш можно так - `ls -lh /var/cache/apt/archives/`
Для очистки кэша используются команды: `sudo apt clean` и `sudo apt autoclean`
Разница заключается в том, что команда **apt clean** полностью очищает кэш скачанных пакетов, а **apt autoclean** удаляет из кэша только устаревшие версии, оставляя актуальные.
Если на системе мало места, **очистка кэша** может помочь освободить часть диска.
### **Логи apt**
**apt** сохраняет историю установки, удаления и обновления пакетов. Эти сведения можно использовать для диагностики и проверки выполненных действий. Логи APT хранятся в директории **/var/log/apt/**.

Текущая история операций записывается в файл **history.log**. В нём можно увидеть время выполнения операции, запущенную команду и список затронутых пакетов.
Со временем журналы ротируются: старые записи переносятся в отдельные файлы, которые могут быть сжаты для экономии места. Например, предыдущая версия журнала может храниться в файле **history.log.1.gz**. Расширение **.gz** указывает, что файл сжат с помощью **gzip**.
Для распаковки таких файлов используется утилита **gunzip**. Параметр **-c** позволяет вывести распакованное содержимое в терминал, не удаляя и не изменяя исходный файл. Чтобы просмотреть сжатый журнал постранично, используйте команду: `gunzip -c /var/log/apt/history.log.1.gz | less`
### **Архивы tar**
Кроме работы с репозиториями важно понимать, как работать с архивами. Не всё программное обеспечение устанавливается через пакетные менеджеры. Иногда программа распространяется в виде архива: например, с исходным кодом, готовыми бинарными файлами или дополнительными материалами.
В Unix-подобных системах для работы с такими архивами часто используется утилита **tar**. Она позволяет объединять файлы и директории в один архив, а затем распаковывать их обратно. Это удобно при передаче проектов, резервном копировании данных и подготовке файлов к переносу между системами.
Важно не путать обычный архив **tar** и пакет **deb**. Пакет **deb** содержит не только файлы программы, но и служебную информацию для пакетного менеджера: зависимости, скрипты установки, правила удаления и метаданные. Архив **tar** проще: это контейнер с файлами и директориями. После распаковки система не считает его содержимое установленным пакетом. Обычный архив **.tar** просто объединяет несколько файлов в один файл. Форматы вроде **.tar.gz**, **.tar.xz** и **.tar.bz2** дополнительно сжимают данные, чтобы архив занимал меньше места.
Распространённые форматы архивов:
- **.tar** - обычный tar-архив без сжатия;
- **.tar.gz** или **.tgz** - tar-архив, сжатый с помощью gzip;
- **.tar.xz** - tar-архив, сжатый с помощью xz;
- **.tar.bz2** - tar-архив, сжатый с помощью bzip2.
Основные параметры утилиты **tar**
- **-t** - показать содержимое архива;
- **-x** - распаковать архив;
- **-c** - создать архив;
- **-f** - указать файл архива;
- **-z** - использовать gzip-сжатие;
- **-J** - использовать xz-сжатие;
- **-C** - распаковать архив в указанную директорию.
Рассмотрим популярные случаи:

- `tar -tf archive.tar` - посмотреть содержимое архива **.tar**;
    
- `tar -tzf archive.tar.gz` - посмотреть содержимое архива **.tar.gz**;
    
- `tar -xf archive.tar` - распаковать архив **.tar**;
    
- `tar -xzf archive.tar.gz` - распаковать архив **.tar.gz**;
    
- `tar -xJf archive.tar.xz` - распаковать архив **.tar.xz**;
    
- `tar -xzf archive.tar.gz -C /opt` - распаковать архив **.tar.gz** в директорию **/opt**;
    
- `tar -cf project.tar project/` - создать архив **.tar** из директории **project/**;
    
- `tar -czf project.tar.gz project/` - создать архив **.tar.gz** из директории **project/**;
    
- `tar -cJf project.tar.xz project/` - создать архив **.tar.xz** из директории **project/**.
Если нужно видеть список файлов во время создания или распаковки, можно добавить параметр **-v**: `tar -czvf project.tar.gz project/`. Это может быть полезно для обучения или диагностики, но для больших архивов вывод может быть слишком длинным.

На практике работа с архивом обычно выглядит так: пользователь скачивает архив, проверяет его содержимое, распаковывает файлы, переходит в появившуюся директорию и изучает документацию проекта. После этого уже можно переходить к установке или сборке, если она требуется.
### **Ручная сборка ПО**
На протяжении всей статьи мы устанавливали программы через пакетный менеджер - это удобно, быстро и безопасно. В реальной практике возникают ситуации, когда этот способ не подходит. Например, нужной программы может не быть в репозиториях, требуется самая свежая версия с определёнными параметрами сборки, или необходимо срочно внести исправление в исходный код для устранения уязвимости. В таких случаях программу собирают вручную из исходного кода.

У такого подхода есть ряд существенных недостатков. Сборка может занимать значительное время, особенно для крупных проектов. Все зависимости приходится разрешать вручную - пакетный менеджер в этом процессе не участвует. На сервере должно быть установлено сборочное окружение, что не всегда допустимо на продакшен-системах.

Именно поэтому ручная сборка применяется только тогда, когда установка через пакетный менеджер невозможна или не отвечает требованиям задачи. В повседневной работе предпочтение всегда отдаётся **apt** и репозиториям.
